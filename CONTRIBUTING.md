# Как внести вклад в руководство по стилю

Спасибо, что помогаете улучшать руководство. В этом документе описано, как предложить изменение, оформить коммиты, пройти ревью и собрать сайт локально.

## Как предложить изменение

1. Если изменение крупное или спорное, сначала создайте Issue и опишите проблему: какое правило не работает, какой пример это показывает.
2. Создайте ветку от актуальной `main`. Имя ветки начинается с типа изменения: `docs/accessibility`, `fix/broken-links`, `ci/add-link-check`.

    ```bash
    git switch main
    git pull
    git switch -c docs/<короткое-описание>
    ```

3. Внесите изменения и проверьте их локально: `npm run lint` и `npm run build`.
4. Сделайте коммит по правилам из раздела «Требования к коммитам».
5. Отправьте ветку и создайте Pull Request в `main`:

    ```bash
    git push -u origin docs/<короткое-описание>
    ```

6. Заполните шаблон Pull Request: что изменено, зачем и как проверено.

## Требования к коммитам

Сообщения коммитов пишем по спецификации [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/). Формат:

```text
<тип>(<область>): <краткое описание>

<подробное описание — необязательно>

<сноски — необязательно>
```

Правила:

- Краткое описание пишем по-русски, со строчной буквы, в повелительном наклонении, без точки в конце: «добавить правило о кавычках».
- Длина первой строки — не больше 72 символов.
- Один коммит — одно логическое изменение.
- Ломающее изменение (например, правило, которое делает недействительными старые документы) помечаем `!` после типа и сноской `BREAKING CHANGE:`.

| Тип | Когда использовать |
| --- | --- |
| `docs` | Изменение текста руководства |
| `feat` | Новая возможность сайта или проверки |
| `fix` | Исправление ошибки: битой ссылки, неверного примера |
| `style` | Форматирование без изменения смысла |
| `refactor` | Перестройка структуры разделов без изменения правил |
| `ci` | Изменение GitHub Actions |
| `build` | Изменение зависимостей и сборки |
| `chore` | Служебные изменения |

Области (scope): `tone`, `spelling`, `formatting`, `markdown`, `templates`, `recommendations`, `glossary`, `accessibility`, `lint`, `ci`, `deps`.

Примеры:

```text
docs(glossary): добавить термин «спринт»
fix(formatting): исправить пример с кавычками в ОФ-9
ci: добавить проверку сообщений коммитов
docs(tone)!: запретить обращение на «ты»

BREAKING CHANGE: все документы с обращением на «ты» нужно исправить.
```

Сообщения коммитов в Pull Request проверяет commitlint.

## Процесс ревью

1. Pull Request можно сливать, когда выполнены условия:
    - все проверки CI прошли успешно;
    - есть минимум одно одобрение (Approve) от участника, который не автор изменений;
    - все обсуждения закрыты.
2. Ревьюер проверяет:
    - соответствует ли текст правилам руководства;
    - не противоречит ли новое правило существующим;
    - есть ли у правила пример и способ проверки;
    - добавлена ли новая страница в навигацию.
3. Ревьюер оставляет комментарии к конкретным строкам и ссылается на коды правил, например «ОП-2: нужны кавычки-ёлочки». Предложения по тексту удобно оформлять через **Add a suggestion**.
4. Автор отвечает на каждый комментарий: исправляет и пишет, в каком коммите, или объясняет, почему не согласен.
5. После одобрения автор выполняет слияние **Squash and merge** или **Create a merge commit** и удаляет ветку.
6. После слияния в `main` сайт публикуется автоматически. Проверьте результат на GitHub Pages.

## Как запустить локальную сборку

Нужны Node.js 20+ и Python 3.10+.

```bash
npm ci
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
npm run lint
mkdocs serve
```

Сайт откроется по адресу `http://127.0.0.1:8000` и будет обновляться при сохранении файлов. Перед отправкой изменений соберите сайт в строгом режиме: `npm run build`. Сборка завершится с ошибкой, если есть битые ссылки или страница не добавлена в навигацию.

## Как добавить новый раздел

1. Создайте файл в папке `docs/`. Имя файла — латиницей в kebab-case: `docs/accessibility.md`.
2. Начните файл с заголовка первого уровня. Каждому правилу присвойте код с префиксом раздела и постоянный якорь: `## ДС-1. Пишите простым языком {#ds-1}`.
3. Опишите каждое правило по структуре: формулировка, пример «Не пишем / Пишем», способ проверки.
4. Добавьте страницу в навигацию `nav` в файле `mkdocs.yml`.
5. Добавьте префикс раздела в таблицу на главной странице `docs/index.md`.
6. Если правила можно проверить автоматически, добавьте их в `prh.yml` или `.textlint/rules/ru-style.js`.
7. Запустите `npm run lint` и `npm run build`, затем создайте Pull Request.
