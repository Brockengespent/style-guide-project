# Документация API

Раздел отвечает на вопрос: как описывать методы REST API ДелоТрек, чтобы разработчик интеграции отправил первый запрос без помощи поддержки. Правила дополняют [шаблон описания метода API](doc-templates/api-method.md) и рекомендацию [ТР-4](recommendations.md#tr-4).

## АП-1. Один метод — одна страница {#ap-1}

Каждый метод описываем на отдельной странице по шаблону. Заголовок называет действие глаголом в инфинитиве, а не адрес метода.

<!-- textlint-disable -->

| Не пишем | Пишем |
| --- | --- |
| GET /tasks | Получить список задач |
| Метод для удаления задачи | Удалить задачу |

<!-- textlint-enable -->

Проверка: ревью.

## АП-2. Показываем метод и путь в блоке кода {#ap-2}

Сразу под заголовком приводим HTTP-метод и путь в блоке кода с языком `http`. Параметры пути пишем в фигурных скобках.

```http
DELETE /api/v1/tasks/{task_id}
```

Проверка: ревью.

## АП-3. Описываем параметры таблицей {#ap-3}

- Столбцы таблицы: «Параметр», «Тип», «Обязательный», «Описание».
- Тип пишем так же, как в спецификации OpenAPI: `string`, `integer`, `boolean`, `array`.
- Для необязательного параметра указываем значение по умолчанию.
- Для дат указываем формат ISO 8601, для чисел — допустимые границы.
- Если значений немного, перечисляем их все.

| Параметр | Тип | Обязательный | Описание |
| --- | --- | --- | --- |
| `status` | `string` | Нет | Статус задачи: `new`, `in_progress` или `done`. По умолчанию `new`. |
| `assignee_id` | `integer` | Нет | Идентификатор исполнителя. |
| `due_date` | `string` | Нет | Срок выполнения в формате ISO 8601, например `2026-11-01`. |
| `limit` | `integer` | Нет | Сколько задач вернуть: от 1 до 100. По умолчанию 20. |

Проверка: ревью.

## АП-4. Даём рабочие примеры запроса и ответа {#ap-4}

- Пример запроса — команда `curl`, которую можно скопировать и выполнить, подставив свой токен.
- Пример ответа — настоящий ответ метода в формате JSON с отступом в два пробела.
- Кроме успешного ответа, приводим пример ответа с ошибкой: разработчику он часто нужнее.
- Данные в примерах вымышленные, но правдоподобные: «Подготовить отчёт», а не «test123».

Пример ответа с кодом 401:

```json
{
  "error": "unauthorized",
  "message": "Токен не передан или истёк"
}
```

Проверка: ревью.

## АП-5. Описываем все коды ответов {#ap-5}

Для каждого кода ответа пишем, когда он возникает и что делать разработчику. Так описание ошибки отвечает на вопросы из правила [ТР-1](recommendations.md#tr-1).

| Код | Когда возникает | Что делать |
| --- | --- | --- |
| 200 | Запрос выполнен | — |
| 401 | Токен не передан или истёк | Получите новый токен и повторите запрос |
| 404 | Задачи с таким `task_id` нет | Проверьте идентификатор задачи |
| 429 | Превышен лимит запросов | Повторите запрос через время из заголовка `Retry-After` |

Проверка: ревью.

## АП-6. Не публикуем секреты {#ap-6}

Токены, ключи и пароли в примерах заменяем заглушками в угловых скобках: `<токен>`. Не указываем адреса внутренних серверов и реальные идентификаторы клиентов.

Проверка: ревью.

## АП-7. Предупреждаем об устаревших методах {#ap-7}

Устаревший метод не удаляем из документации сразу. В начало его страницы добавляем блок `warning` с датой отключения и ссылкой на метод-замену:

```markdown
/// warning | Метод устарел
Метод перестанет работать 1 марта 2027 г. Используйте метод «Получить список задач».
///
```

После даты отключения страница остаётся в документации ещё шесть месяцев, чтобы интеграции успели перейти на новый метод. Затем страницу удаляем.

Проверка: ревью.
